## Apex records (not required by EmailIt, but relevant to how Gmail/Outlook judge `noreply@founders.click`)

| query | answer |
|---|---|
| `founders.click TXT` | NODATA — **no SPF at the apex** |
| `founders.click MX` | NODATA — **no MX at the apex** (the From domain has no inbound mail route) |
| `founders.click A` | 104.21.75.79, 172.67.217.144 (Cloudflare) |
| `www.founders.click A` | 172.67.217.144, 104.21.75.79 |
| `mail.founders.click` TXT/MX, `emailit._domainkey.mail.founders.click` | NXDOMAIN (no `mail.` subdomain registered) |
| `send.`, `noreply.`, `em.`, `email.founders.click` TXT | NXDOMAIN |
| `_dmarc.emailit.founders.click` TXT | NXDOMAIN (DMARC is at the apex, correct) |

Correction to the Phase-2 precondition note ("NO SPF record on founders.click"):
EmailIt does not put SPF on the apex; it puts it on `emailit.founders.click`, where it
is present. The apex-SPF absence is a deliverability nuance, not an EmailIt
verification blocker — EmailIt's own SPF check targets `emailit.founders.click`,
and the SMTP envelope sender (return-path) for EmailIt mail is under that
subdomain (that is what the required MX on it is for), so SPF alignment is with the
subdomain, DKIM `d=founders.click` gives DMARC alignment.
